**AC-4 content signatures can be trusted by public key, a failed check says why in one word, and the C API signs and verifies.** `forge ac4-verify` and `decode`'s `verify-content` / `check-content` take `trust-key=<public key file>` (a PEM "PUBLIC KEY" block or DER, what `openssl pkey -pubout` writes): a chain whose signing certificate carries that P-256 key is anchored, with every other check still run, so a trusted key never rescues a changed stream. The report ends in a `result:` line, one of `valid`, `untrusted`, `no-signature`, `unreadable`, `chain-rejected`, `signature-invalid`, `content-altered`, `metadata-altered` or `refused-by-policy` (the exit code is still 0 or 6 for `ac4-verify`); the same reduction is `iclforge::base::crypto::classify(report)`, `VerifyPolicy::trust_keys` is the library side, and `parse_p256_public_key` reads the file. `iclforge_ac4_sign_stream` and `iclforge_ac4_verify_stream` in the C API sign and check an in-memory raw `.ac4` stream with the caller's own key, certificate bundle and trust anchor or key, nothing read from disk. The signature is made with your key and chains to your certificates, not to Dolby's or PACE's trust root: a licensed Dolby decoder will not take it as Dolby-authentic, and nothing here obtains or imitates a Dolby-issued signature (see the threat-model note in the object-signing page). Tests sign then verify through the library, the command line and the C API, and tamper with the audio, the signer information, the signature and the trusted key.
