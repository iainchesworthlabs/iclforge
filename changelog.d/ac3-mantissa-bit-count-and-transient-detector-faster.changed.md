**The AC-3 and E-AC-3 encoders encode 5.1 about 14 % faster (AC-3) and 2 to 8 % faster (E-AC-3), with the same bytes out.** Two parts of the encode were the cost: the mantissa bit count that the encoders' bit budgeting runs, and the transient detector that decides block switching. The bit count had a branch per bin on the bin's bit allocation, which the CPU mispredicted often; it now adds one table entry per bin to four packed counters and reads the four totals out at the end, which takes 971 ns down to 496 ns for a 5.1 block on a Ryzen 9 5950X (median of 7 runs, 1,104 ns to 510 ns on a second pair). The transient detector kept the two filter stages' memory in the detector object and read and wrote it through memory on every sample; it now holds it in registers for the 256-sample pass, reduces each block of 64 to its peak as the samples come out of the filter instead of storing them and sweeping the array again, and so no longer keeps a 2 KB (1 KB at single precision) array on the stack. The filter does the same floating-point operations in the same order, so every decision and every encoded byte is unchanged: `forge encode`, `eac3-encode` and `atmos-encode` outputs are identical to the previous build at 24 bit rates and layouts. Encoding 5.1 with the fast transform: 0.357 ms a frame down to 0.303 ms on a quiet machine (`plain_51_fast_mdct`, median of 7 runs, a second pair 0.355 to 0.306); `eac3_51_auto` and `eac3_stereo_auto` also move down, by 1 to 8 % across the four pairs measured.
