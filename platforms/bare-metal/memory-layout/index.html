    ESP32 memory layout¶

    Where the flash and the RAM go on the three ESP32 development kits that run the Hearth sink firmware (hearth_sink): an ESP32-S3-DevKitC-1-N16R8, an ESP32-C6 with 4 MB or 16 MB of flash, and an ESP32-P4 of chip revision v1.x, or v3.x with the lyric panel. This page is for a developer who is porting the firmware to a board, tuning one or debugging one. It summarises figures that the board pages (ESP32-S3, ESP32-C6, ESP32-P4) and the sink guides measure and explain, and it links to each measurement.

    Reading the figures¶

    Every image here is built from a profile: a locked list of sdkconfig fragments, the values of the keys that decide where memory goes, and the budgets the image is held to. profiles.json holds the seven profiles, and the firmware's README lists them. A value on this page that comes from a profile is a setting. A value with a build and a date beside it is a measurement.

    The terms:

    • Static internal RAM is what idf.py size reports as DIRAM: the code ESP-IDF places in RAM (interrupt handlers and what runs while the flash cache is off), .data (initialised variables) and .bss (variables that start at zero). It is taken before app_main runs.
    • The internal heap is what is left of internal RAM for malloc, task stacks, Wi-Fi's buffers and the decoder. "Free" is heap_caps_get_free_size(MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT).
    • The largest free block is the largest single allocation the internal heap can make. The heap is in regions and fragments as it is used, and a task's stack is one allocation, so this figure decides whether a stack or a ring can be made.
    • PSRAM is external RAM behind the data cache. With CONFIG_SPIRAM_USE_MALLOC, malloc places a block by its size: under CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL bytes it tries internal RAM first, at or over that it tries PSRAM first, and either falls back to the other.
    • A baseline is the board suite's record for a profile, in firmware/hearth-sink/baselines/: a bench board restarted eight times, then five plays of each stream. Its boot figures are the board's budget: line, printed once Wi-Fi and the Sendspin player are up, and a range on this page is the range over the eight boots.

    The baselines the tables cite, with the image each was recorded on (the dates are UTC):

    • s3-n16r8: board S3a, v0.10.0-beta.1-5587-g2a14b2b96, 2026-10-29, with the AC-4 decoder and the 64 KB data cache (until then the release image had neither, recorded 2026-10-12 at v0.10.0-beta.1-4565-gc3878ebaa, and s3-n16r8-ac4 was its own profile, S3a, v0.10.0-beta.1-4723-ge3da66cb3, 2026-10-12: the figures below marked s3-n16r8-ac4 are that profile's).
    • c6-16mb: the C6 board, v0.10.0-beta.1-4738-g357812dae, 2026-10-12.
    • p4-rev1 (until 2026-10-29 p4-rev1-ac4): board P4a, v0.10.0-beta.1-4723-ge3da66cb3, 2026-10-12.

    c6-4mb and p4-rev3 have no bench board and no baseline. The p4-rev3 image has not run on a v3.x chip or on a panel: its figures are a build's, and the screen's cost was measured on a v1.3 board with no panel.

    The flash map¶

    Every board has two application slots, ota_0 and ota_1, and an otadata partition that says which of them boots. The bootloader is below the partition table, which is at 0x8000: from 0x0 on the S3 and the C6, and from 0x2000 on the P4.

    partitions.csv: 16 MB of flash (the S3, the P4, and a C6 built with sdkconfig.flash16mb)

name      type  offset    size                 what
nvs       data  0x009000  0x006000    24 KiB   the board's name, network and pairings
phy_init  data  0x00F000  0x001000     4 KiB
otadata   data  0x010000  0x002000     8 KiB   which application slot boots
ota_0     app   0x020000  0x400000     4 MiB   application slot; a USB flash writes this one
ota_1     app   0x420000  0x400000     4 MiB   application slot
coredump  data  0x820000  0x010000    64 KiB   a panic's core dump (the S3 image writes none)
audio     data  0x830000  0x040000   256 KiB   the sample stream the partition source reads
storage   fat   0x870000  0x040000   256 KiB   the FAT volume of the fatfs source
reserve   data  0x8B0000  0x400000     4 MiB   unused; the table ends at 0xCB0000

partitions_c6.csv: 4 MB of flash (any C6 module)

nvs       data  0x009000  0x006000    24 KiB
phy_init  data  0x00F000  0x001000     4 KiB
otadata   data  0x010000  0x002000     8 KiB
ota_0     app   0x020000  0x1E0000  1.875 MiB
ota_1     app   0x200000  0x1E0000  1.875 MiB
coredump  data  0x3E0000  0x010000    64 KiB   the table ends at 0x3F0000; no audio, no storage

    The two files are partitions.csv and partitions_c6.csv; the OTA plan has the reason for each line.

    • An update over the network writes the slot that is not running, and the new image boots on trial. A reset before the image accepts itself boots the other slot again (CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE). Sink firmware has the sequence.
    • A USB flash writes the bootloader, the partition table, an empty otadata, the application into ota_0, and audio and storage. An empty otadata boots ota_0 with nothing on trial.
    • Nothing writes nvs, which is at 0x9000 in both tables, so a board keeps its name, its network and its pairings through a USB flash and through an update.
    • The partition table, the flash size setting and the bootloader change only over USB. The flash mode (DIO or QIO) is the bootloader's, so it changes only over USB too.

    Heap floors, and how a refusal is reported¶

    A decoder that cannot allocate calls abort(), which restarts the board and ends its Sendspin session. The floors refuse a play before that point. Each is the least a play can need, and a wider stream asks for more.

    • The boot budget line. After the network is up and the Sendspin player has started, the board prints budget: when=boot net=1 internal_free=... largest=... ask_ring=... ask_decode_stack=... ask_fetch_stack=... ask_total=... ask_biggest=... headroom=... floor=... verdict=.... The asks are the ring and the stacks an HTTP play takes from internal RAM in this build, and headroom is the largest free block less the biggest ask. verdict is ok, short-block (no free block holds the biggest ask), short-total (not that much free in all) or below-floor (the HTTP play floor would refuse).
    • The HTTP play floor, CONFIG_ICLFORGE_EXAMPLE_PLAY_MIN_FREE_BYTES: 160,796 in both C6 profiles and 0 in the others. A POST /play that finds less internal RAM free fails at once: GET /status has "failed": true, "why": "memory" and the bytes that were free in error, and the console has player: a play here needs 160796 bytes of internal RAM free and N are: refused (CONFIG_ICLFORGE_EXAMPLE_PLAY_MIN_FREE_BYTES). A Sendspin stream is not tested by it.
    • The AC-4 floor: 286,365 bytes of heap, PSRAM counted, which is the least any AC-4 stream has needed (the 2.0 probe fixtures' peak). Under it an HTTP play fails with "why": "memory" and player: AC-4 needs at least 286365 bytes of heap and N are free: refused. A Sendspin stream's chunks are refused with the same line under the name burst player:. It came with #1233, and in practice a part with no PSRAM is the one under it.
    • Coded channels over Sendspin, CONFIG_ICLFORGE_EXAMPLE_SENDSPIN_MAX_CODED_CHANNELS: 2 on the C6. A wider syncframe is refused before a decoder is made for it, the console says burst player: refusing a 6-channel syncframe: more than the 2 this part decodes in this build once a stream, and each refused chunk counts as invalid.
    • A lyric document is taken only while internal RAM has three times its size and 8,192 bytes free (twelve times its size when PSRAM has no room for it). Otherwise the console says sendspin: lyrics not taken: N bytes of internal heap free, M needed and the stream plays without lyrics.
    • An allocation that fails anyway prints heap: <function> could not allocate N bytes (caps 0x...); internal free X, largest Y before the abort. tools/checks/check_esp_console.py fails a console capture that has one.

    Under QEMU, CI holds the S3's stream set and its Sendspin shape to 20,480 bytes of internal RAM free at the least, and the decode lane's shape to 12,288 (ESP32-S3).

    The "least free" figures are low because of where allocations go: those under 16 KB try internal RAM first, so the AC-3 and E-AC-3 decoders and the network fill what is free and then spill to PSRAM. What is added to the player's internal allocations is the risk, and the sink guide says how the console reports it.

    ESP32-C6 (4 MB and 16 MB)¶

    One core, no FPU and no PSRAM: the code runs from flash, and the player's buffers, Wi-Fi's receive buffers and the decoder come out of the same 512 KB. The two images differ in the partition table alone. On this board the limit is memory, and the sink plays AC-3 and E-AC-3 of up to two coded channels (An ESP32-C6 sink).

    Rules of thumb¶

    What to keep out of internal RAM¶

    • Any single block near the largest free block. On an S3 with Wi-Fi up that is 31,744 bytes. A 32 KB stack or a ring goes to PSRAM by name (CONFIG_ICLFORGE_EXAMPLE_DECODE_STACK_IN_PSRAM, ..._SENDSPIN_DECODE_STACK_IN_PSRAM, ..._RING_IN_PSRAM) and is asked for with PSRAM capabilities. malloc's size rule does not apply to a task's stack, which FreeRTOS takes from internal RAM unless the task is created with capabilities.
    • Function-local static tables of optional coding tools. They are .bss in every image, whether or not a stream uses the tool: 27,776 bytes on the C6 (#1474). Make the table a member of the heap object that exists only while the tool runs, or a constant in flash.
    • Constants, where a cache miss is cheap. On the S3 and the P4 the code and constants run from PSRAM. On the C6 a table the decoder reads in every block stays in .data, because the 16 KB cache is shared with the code (#1511).
    • thread_local buffers. FreeRTOS takes each task's thread-local area from that task's stack and sizes it from the whole image. A 32 KB thread_local scratch made every task's area 32 KB, ESP-IDF's IPC task has a 1 KB stack, and the S3 application failed before app_main (What the port required from the library).
    • Documents made of many small blocks. A parsed lyric document is about ten times its text at the peak, and every block is under the 16 KB limit. The Sendspin player reads and holds it with PSRAM first for that one task (PsramScope).
    • Buffers that keep their largest size. Three Sendspin receive buffers kept the capacity of the largest message they had held: an 8,000-byte lyric document left 12.7 KB of an S3's internal heap taken for the rest of the connection. A JSON document over 4,096 bytes now releases them, and audio chunks keep theirs so that a stream does not allocate for every chunk (#1408: S3a, 2026-10-12).
    • The P4's low-power SRAM. A project of its own that decodes on a P4 sets CONFIG_ESP_SYSTEM_ALLOW_RTC_FAST_MEM_AS_HEAP=n.
    • A second graphics heap. LVGL's allocator is PSRAM alone (CONFIG_LV_USE_CUSTOM_MALLOC), because ESP-IDF's malloc would put every block under 16 KB in internal RAM.

    Two things belong in internal RAM. DMA buffers are allocated by their capabilities and no limit moves them. And moving the decoder's working memory to PSRAM costs time: 1.08 to 1.24 times a frame on the P4, and enough on the S3's E-AC-3 decode to underrun. The S3's 512-byte rule holds for AC-4 plays alone, where the alternative left Wi-Fi with 0.4 to 5 KB.

    How to measure¶

    Static RAM, from a build:

    • idf.py size --format json2 gives DIRAM, and python tools/hearth/sink_profile.py verify <profile> --build-dir <dir> --size-json <file> holds it, the application and the bootloader to the profile's budgets. CI runs both for every profile it builds.
    • idf.py size-components and idf.py size-files give the same by archive and by object file.
    • For .bss by input section, read the linker map in the build directory. An archive's own total can differ from the linked image's: the three copies of one table in libiclforge_ac3_minimal.a are one weak symbol after the link, 39,864 bytes in the archive and 39,752 in the image. tools/checks/footprint_report.py reads a GNU ld map the same way for the Cortex-M3 probe.
    • idf.py size's "remain" is the linker's estimate of the heap. On the S3 probe it said 239,164 where the allocator reported 304,680.

    The heap, from a running board. The firmware has no heap route; it prints these lines, and GET /log returns the console's recent output (the last 16 KiB on a board with PSRAM, 2 KiB on the C6; python tools/hearth/ota.py log --host <board> --follow follows it):

    • budget: at boot and when a network comes up later: free, the largest block, the asks and the verdict (above).
    • sendspin: player up with internal heap N free, largest block M when the Sendspin player starts.
    • heap: internal free N (largest block M), psram free P when an HTTP play has opened its source, before the decoder allocates.
    • sendspin.progress ... heap_free=N heap_largest=M heap_least=L every 125 chunks of a Sendspin stream, and sendspin.stream= ... heap_free=L when it ends: the least internal heap free while the stream played.
    • stream.decode_stack_free=N at the end of an HTTP play, and decode_stack_free and server_stack_free in GET /status's sendspin object.
    • ac4.heap internal_start=... internal_least=... internal_peak=... psram_start=... psram_least=... psram_peak=... at the end of an AC-4 play.
    • GET /hardware has psram_bytes, profile and profile_hash, and GET /firmware has the partition table and both slots.

    To hold a board to figures:

    • tools/checks/check_esp_console.py --min-heap-free <bytes> --min-budget-headroom <bytes> on a console capture. --budget-verdict below-floor is the C6's.
    • python tools/hearth/board_suite.py run --profile <profile> --restart --boots 8 --repeat 5 with --record or --compare <baseline>, on a booked bench board.
    • tools/checks/run_esp32s3_probe.sh, and with --ac4, for the decoder alone under QEMU: peak heap for each fixture and, for AC-4, the internal RAM and PSRAM each took.
    • On an S3 image with AC-4, ?below=N in a play's location sets that play's allocation limit.

    Traps¶

    • An update over the network overwrites the slot that is not running. One push leaves the image the board had as the one to go back to. A second push overwrites it. After two pushes the image the board was found on is in neither slot, and restoring it means pushing that image again.
    • A P4 board's chip revision decides the image. A v1.x image refuses a v3.x chip and the other way round. GET /hardware and esptool chip-id say which a board is, and ota.py chooses from them (Sink firmware). On v1.x, 400 MHz asserts in a boot loop.
    • The flash mode is the bootloader's. An application built for QIO runs at DIO speed under a DIO bootloader, and an update over the network keeps the bootloader. A board takes QIO with one USB flash that includes its bootloader.
    • The P4's bootloader has 24,576 bytes. A new ESP-IDF, a log level or a chip revision can take it over, and the build then fails.
    • The largest free block decides an allocation. A C6 with 11,016 bytes free could not allocate a 1,848-byte Wi-Fi buffer: no block was over 1,824.
    • QEMU has no Wi-Fi. The S3's release shape under QEMU boots with 226,679 bytes free and a 135,168-byte largest block, where a board has about 86,000 and 31,744. A stack that cannot be made on a board is made there.
    • A low-water mark depends on what played before. On an S3 an AC-3 stream after an E-AC-3 one read 7.2 KB free where the first stream of a boot read 58 to 60 KB. Record a board's figures after a restart, in a fixed order.
    • Freeing RAM can defeat a floor. The C6's HTTP play floor refused every play only while the board had too little free to pass it. With 27,776 bytes back a play started and failed, and the floor went from 134,008 to 160,796.
    • CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL reserves nothing for long. ESP-IDF v6.1 lets ordinary small allocations take the reserve once the rest of internal RAM is full.
